# Modeling assumptions (Phase 1)

- Zone-level capacity screening only: one aggregate hourly baseline vs one capacity value. No feeder topology, voltage, protection, N-1, or power flow (CLAUDE.md §1.4, ADR-001).
- Historical replay is not a forecast (ADR-002). Five years = 43,824 historical operating conditions.
- Capacity pressure states: normal < 85% of capacity; approaching limit 85–100%; constrained > 100% (`apps/web/src/lib/pressure.ts`). Unresolved/resolved states arrive with flexibility in Phase 4.
- Playback speed: 1x = one simulated hour per real second; 10x/100x/1000x scale linearly.
- Times are shown as EST (fixed UTC-5), matching IESO's reporting convention, never browser-local time.

## Phase 2
- Net load = baseline + project increment (local generation term reserved, currently 0). A violation is net load strictly above capacity; exactly equal is not a violation.
- Data centre: constant 24/7 nominal MW, 0 < MW <= 500, no flexible compute (flexibilityFraction must be 0 until the optimizer exists). Multiple data centres add.
- Event windows are runs of consecutive constrained hours; `end` is exclusive; a window that crosses midnight counts 2 days.
- `percentWithinCapacity` = share of tested hours within capacity (never called "reliability").
- Scenarios are stored in memory (lost on API restart; the UI recreates a baseline). The world/baseline data is read-only.

## Phase 3 (DER agents)
- The population is generated from the world pack seed; each agent TYPE uses its own SeedSequence child, and states are pure functions of (seed, agent, time), never of call order.
- Participation: each agent has a fixed uniform draw; participating = draw < rate (rates from the world pack, overridable per scenario). Raising a rate only ADDS participants. Solar is never a flexibility participant.
- **No double counting.** The observed baseline already contains historical consumption (EV charging, HVAC, battery routines) and solar. Agents are an *attribution* of that baseline plus flexibility around it: baseline = background residual + EV + building HVAC + battery charging - solar. The net-load equation is untouched by agents. Solar potential is always 0 (`already_in_baseline`). Controllable attributed load is calibrated to stay <= 25% of the baseline (`CONTROLLABLE_CAP`).
- Battery: at-rest routine (overnight charge, hold, 16-20h partial self-supply). Potential = min(inverter headroom above its at-rest flows, usable energy above reserve / window). EV fleet: at-rest unmanaged charging from arrival; potential = shiftable fraction of sustained charging, capped so deferred energy is recoverable before departure. Building: attributed HVAC share (driven by a heat index from the baseline shape) x shed fraction x comfort budget, averaged over the window if it exceeds max curtailment hours.
- Simplifications: schedules use fixed EST (no daylight-saving shift); sky/cloud is a per-day pseudo-random factor, not observed weather; rebound is recorded but not yet simulated (no dispatch).
- Potential is what agents COULD offer. Coordination, optimization and dispatch arrive in Phases 4-5.

## Phase 4 (single-event coordination)
- Scope: ONE event window (<= 48 h) + a recovery tail (default 8 h, <= 12). No multi-event coordination, no project-level feasibility claim.
- Eligible agents: participating (draw < rate) AND available in that hour (per-hour flags from each agent's own state); the rest are excluded with a reason. Solar is informational and never enters the model.
- Deterministic OR-Tools SCIP MILP, 1 thread, stable agent ordering, per-agent epsilon tie-breaks. Variables: battery extra charge/discharge (SOC deviation carried forward, reserve, inverter limits net of its at-rest flows), EV defer/recover (energy delivered by departure, shiftable fraction, charger limit), building shed (binary duration budget, power cap, comfort budget baked into the cap, shed only inside the event window, rebound after).
- Objective: minimize residual energy above capacity (weight 1000/MWh, +5% per MW of pre-dispatch deficit so the worst hours are reduced first), then dispatch cost (battery throughput 1, EV shift 0.5, building shed 2 per MWh). **Do-no-harm:** no hour may end worse than before dispatch and hours within capacity must stay within capacity, so rebound/recovery/recharge can never create new violations.
- Status: `resolved` = no violation hour left in the window or tail; `partially_resolved` = energy above capacity cut by >= 0.5% but violations remain; `unresolved` = no meaningful reduction.
- An independent validator re-derives every physical constraint from the solution (battery SOC/reserve/inverter, EV energy/deadline/charger/shiftable, building power/duration/rebound, no-hour-worse, slack accounting); results carry `checksPassed` and `reconciled` (optimized = pre-dispatch - sum of per-agent dispatch).
- Simplifications: hourly steps; a battery's SOC deviation from its at-rest routine is not recovered inside the horizon (conservative); EV connectivity and rest charging are hour-averaged from four samples; unavailable-at-hour-start batteries/buildings get zero capability for that hour.

## Phase 5-6 (owner/operator agents, agentic mode)
- Two agent concepts: **physical DER models** (78, deterministic, unchanged) and **owner/operator agents** (18, Modeled behavior). Solar (8) has no owner; it is context only. Every flexible asset (20 batteries, 14 EV fleets, 36 buildings = 70) belongs to exactly one owner.
- Ownership is deterministic: seeded permutation of each asset type, split into 5 battery operators, 5 EV operators, 8 building portfolios (`owners/grouping.py`). Owner preferences are seeded draws inside type-specific ranges and are all Modeled: min compensation ($/MWh), target margin, price sensitivity, reserve preference, comfort priority, driver-satisfaction priority, degradation sensitivity, max event hours, deadline strictness, risk tolerance, participation tendency.
- **Manual mode** = existing participation sliders (participation draw < rate), no LLM. **Agentic mode** = participation emerges from owner offers on a `FlexibilityRequest`; the participation draw is not used (only owner decisions). The physical limits are identical in both modes.
- `FlexibilityRequest.requestedMwByHour` = pre-dispatch deficit over the event window (Derived). Incentive = a $/MWh price ceiling CapacityOS will pay; offers priced above it are "priced out" (a counteroffer) and never enter the optimizer.
- Offer = per-asset structured time blocks (hour offsets inside the event window, MW) + one price ($/MWh) + conditions. An offered MW profile is a **cap** on the delivering variable (battery discharge, EV deferral, building shed); the optimizer still chooses how much, and recharge/recovery/rebound stay free outside the offer (they are the physics the validator/optimizer already own).
- **Physical validation** (deterministic; independent of the LLM): ownership, asset exists and is flexible, blocks inside the event window, price sanity, per-hour availability/ceilings, and joint feasibility of delivering the WHOLE offered profile at once via a single-asset LP (max scale lambda s.t. the asset delivers lambda x offer under the same SOC/reserve/inverter, EV energy/deadline/charger/shiftable and building power/duration/comfort/rebound constraints as the clearing model). lambda < 1 => invalid, with a feasible envelope = 0.999 x lambda x the offered profile and a violation code (`insufficient_usable_energy`, `exceeds_power_limit`, `asset_unavailable`, `deadline_energy_violation`, `exceeds_shiftable_fraction`, `comfort_duration_violation`, ...). One revision turn is allowed; a second invalid offer is rejected and contributes nothing. Duplicate commitments of one asset are rejected.
- **Clearing** = the Phase 4 MILP restricted to accepted assets, with delivering variables capped by the offers and an added price term (price x 0.01 per delivered MWh) so cost is a tie-breaker far below the violation weight (1000/MWh): capacity feasibility is never traded for cost. Clearing cost = sum(price x delivered MWh). Same do-no-harm rule and independent validator.
- Stub provider: deterministic policy from preferences + incentive + event duration (reservation price = min compensation x (1 + degradation/comfort/driver adjustments); offers a preference-scaled fraction of each asset's static ceiling over the best contiguous block within its max event hours; declines below its reservation price; counteroffers within 20%). It ignores joint energy limits on purpose so the validator/revision path is exercised. It is NOT a fit to price -> participation percentages.
- OpenAI provider: structured tool calling; output schema-validated; timeouts, bounded retries, fallback to the stub per owner (recorded). LLM decisions are synthetic behavior, not predictions of real customers. Config: `OWNER_AGENT_PROVIDER`, `OPENAI_API_KEY`, `OWNER_AGENT_MODEL`, `OWNER_AGENT_TIMEOUT_SECONDS`.
- Runs are stored in a bounded in-memory store (50 runs) and can be replayed from recorded owner actions (same offers -> same clearing). Results are Derived; owner decisions are Modeled.
- Still not done after Phase 6: project-level feasibility, recommendations (incl. "at what compensation does enough participation emerge"), reports.

## Phase 7 (historical coordination)
- Scope: only the capacity-event windows of the scenario (59 for the golden 20 MW case), never all 43,824 hours. Non-event hours are untouched except battery gap recharge, which is limited to zone headroom below capacity. No LLM is called: the owner policy is the deterministic stub economics (reservation = min compensation x (1 + priority adj.), ask = reservation x (1 + margin); offers scaled by tendency/reserve/comfort/driver priorities; block = the owner's best contiguous max-event-hours stretch by deliverable MW x criticality) applied per event window, then one joint physical validation + at most one revision per owner per cluster, then one OR-Tools clearing per cluster. `decisionSource = deterministic_owner_policy`, `llmCalls = 0`.
- **Clusters**: consecutive windows with a gap <= `mergeGapHours` (default 24; must be >= `tailHours`, default 8) are merged and simulated jointly over [first start, last end + tail): one battery SOC trajectory, one EV energy balance, a building curtailment budget per 24 h block (Phase 4 single events keep one budget per horizon). A chain longer than 96 h is split at its widest gap (state carried across the split; the tail is truncated at the next cluster so horizons never overlap).
- **State continuity ("no magic reset")**: at the end of a cluster each battery's SOC deviation from its routine (<= 0; a surplus is never carried) is carried. In the gap before the next cluster it recharges hour by hour only with inverter spare power (power - routine charging), only while available, and only within the zone's headroom (capacity - net load, shared across batteries in id order), so recharging can never create a violation; what is still missing at the next start is `carryInBatteryMwh` and constrains its SOC (initial deviation). Building curtailment hours in the previous 24 h reduce the first-block budget. EV deferral must be recovered before departure inside the horizon, so nothing is carried for EVs. Owners have a quota of `maxEventsPerMonth` event windows offered per calendar month (decline code `event_frequency`).
- Per-event status: resolved = energy above capacity after <= tolerance; partially resolved = reduced by >= 0.5%; else unresolved. Severity by the event's worst pre-dispatch deficit: minor < 1 MW, moderate < 3, major < 6, severe >= 6. Year and season (winter Dec-Feb, spring Mar-May, summer Jun-Aug, fall Sep-Nov) are those of the event start (EST); hours, energy and worst deficit are attributed to the event.
- Verification inside every result: event/hour counts equal the scenario analysis; hours and energy after equal a direct scan of all 43,824 hours; no violation appears outside event windows; no event is worse; aggregates reconcile across year/season/severity/DER type; every cluster's physical checks pass.
- Incentive scenarios ($40/$80/$120/custom) are user-selected what-ifs. Nothing searches for an incentive, recommends an action or declares the project feasible (Phases 8-9).
- Simplifications: hourly steps; per-cluster (not per-event) validation and clearing; the monthly quota counts windows offered, not dispatched; carried building state matters only for split chains; dispatch energy is attributed to the window where it is delivered.
